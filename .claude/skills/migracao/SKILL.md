# /migracao — $ARGUMENTS

Referências: 03-como-estender §1.2, §6 e §10.3; regras em `.claude/rules/modelos-e-migracoes.md`;
estilo da casa em `migrations/versions/0001_schema_inicial.py`.

## 1. Antes de gerar

- Os modelos em `app/domain/models.py` já estão no formato final, e a aplicação sobe: o container
  `api` vai ser reconstruído com eles.
- Próximo número: o maior prefixo em `migrations/versions/` + 1, com 4 dígitos (`0002`, `0003`…).
  O `file_template` gera `<rev>_<slug>.py`.

## 2. Gerar

O `api` roda a imagem do último build e monta `./migrations` do host. Sem reconstruir, o
autogenerate compara o banco com os modelos **antigos** e sai vazio — e, se a pasta do projeto
mudou de lugar, o arquivo cai num bind mount morto. Reconstrua sempre:

```bash
docker compose up -d --build --quiet-build --wait api
docker compose exec -T api alembic revision --autogenerate --rev-id 000N -m "<descrição>"
```

Se o `up --wait` falhar, a aplicação não subiu: `docker compose logs --tail 50 api` (quase
sempre um import quebrado no código novo). O entrypoint aplica as migrações existentes no boot,
então o banco de desenvolvimento já está em `head` quando o autogenerate roda.

O autogenerate **não detecta** (escreva à mão, com `alembic revision --rev-id 000N -m "..."`, sem
`--autogenerate`):
- papel novo em `Role`: troca do CHECK `ck_users_role` — molde na receita 10.3;
- mudança só de `server_default` (o `env.py` compara tipos, não defaults);
- dados (backfill): `op.execute(...)`, sempre com o `downgrade` correspondente.

## 3. Revisar o arquivo gerado — sempre

- [ ] Docstring no estilo da 0001 (o que muda e por quê); tire os comentários
      `### commands auto generated by Alembic`.
- [ ] Coluna NOT NULL em tabela que já tem dados tem `server_default`, senão o `ALTER TABLE` falha.
- [ ] Unicidade entre ativos é índice parcial (`unique=True`, `postgresql_where=sa.text("deleted = false")`),
      não `UniqueConstraint`.
- [ ] Nomes de restrição completos dentro de `op.f()` (sem ele a convenção de `domain/base.py` é
      aplicada por cima: `ck_users_ck_users_role`).
- [ ] Valores de enum ou papel escritos à mão na migração, nunca importados de `authz`: a migração
      descreve o schema do momento em que foi escrita.
- [ ] Datas `sa.DateTime(timezone=True)`; FK com `ondelete` e índice.
- [ ] `downgrade()` desfaz exatamente o `upgrade()`, na ordem inversa.
- [ ] Nenhuma migração já compartilhada foi editada.

## 4. Aplicar e validar

```bash
docker compose exec -T api alembic upgrade head
docker compose exec -T api alembic check      # esperado: No new upgrade operations detected.
bash .claude/skills/verificar/verificar.sh migracoes
```

O último passo repete o CI num banco descartável: `upgrade head → check → downgrade base`.

Papel novo: confirme que o banco aceita o valor (o `check` não pega CHECK desatualizado):

```bash
docker compose exec -T db sh -s <<'SQL'
psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -tAc "select pg_get_constraintdef(oid) from pg_constraint where conname = 'ck_users_role'"
SQL
```

## 5. Desfazer (só se a migração não saiu da sua máquina)

```bash
docker compose exec -T api alembic downgrade -1
```

e apague o arquivo. Migração já compartilhada não se edita nem se apaga: crie outra.

## 6. Fechar

Rode `/verificar` (tudo) e informe o número e o nome do arquivo gerado, o que foi ajustado à mão
na revisão e o resultado de cada etapa.
